  ---
  RepoHawk — Comprehensive Codebase & AI-Drive Report

  TL;DR (the verdict first)

  RepoHawk is genuinely AI-driven — not AI-washed. Paste a public GitHub URL and
  a real multi-agent pipeline (compiled LangGraph StateGraphs, not just
  described) clones it, parses it with tree-sitter, embeds it locally, indexes
  it in ChromaDB, then has an LLM generate an AWS-style architecture diagram,
  which a second LLM critiques and can force to be regenerated. A streaming RAG
  chat answers questions with cited source files and highlights the relevant
  diagram node. The LLM layer is production-hardened: per-agent model routing,
  exponential-backoff retry, robust JSON extraction, and a multi-model fallback
  chain.

  That said, the shipped product has drifted meaningfully from the REPOHAWK.md
  spec: rendering moved from Mermaid+D3 to React Flow; the "sacred"
  file_node_index table, the staleness detector, the REPOHAWK.md export, the
  CLI, and the VS Code extension are absent; and a couple of schema columns are
  placeholder-only. It's a strong, working v0.7-ish of the spec's MVP.

  ---
  1. What the app actually is

  A developer pastes a public GitHub repo URL → RepoHawk:

  1. Clones it (git clone --depth=1 via GitPython) into
  /tmp/repohawk/{repo_id}/.
  2. Parses source files with tree-sitter (Py/JS/TS/Go as first-class; ~20 more
  extensions via heuristic chunking), extracting top-level
  classes/functions/imports as semantic chunks — not raw lines.
  3. Embeds those chunks locally (sentence-transformers all-MiniLM-L6-v2,
  384-dim, with an LRU cache) and stores them in an embedded on-disk ChromaDB
  (PersistentClient, one collection per repo, cosine HNSW).
  4. Generates an AWS-style layered architecture diagram: the Architect LLM
  emits typed JSON {nodes, edges} (layers: dev-tools / applications /
  core-services / business-logic / data-storage / external; relations: data-flow
  / control-flow / build-dep).
  5. Critiques it: a second LLM reviews the diagram against the parsed file list
  and can fail it; on failure the graph loops back to the Architect with the
  reviewer's feedback re-injected into the prompt (max 3 attempts, then ship
  best-effort).
  6. Streams every step to the frontend over SSE (clone → parse → embed →
  architect → critique), then renders the diagram in React Flow (zed-zoom,
  node-click, layer grouping) and marks a confidence level from the parsed-file
  ratio.

  Beyond that core loop, the shipped product adds several features not in the 
  original MVP list, each visible in the git log and routers:

  - Auth (JWT access + refresh, bcrypt, email verification + password reset via
  Resend) sitting in front of every endpoint
  (backend/app/api/v1/routers/auth.py, core/security.py, core/dependencies.py).
  - Chat sessions — persistent multi-turn history keyed by chat_sessions /
  chat_messages, with auto-generated session titles.
  - Semantic code search (GET /repos/{id}/search) over the ChromaDB index.
  - Dependency graph parsed from manifests (package.json / requirements.txt /
  pyproject.toml / go.mod), rendered on a second React Flow canvas.
  - A VS Code-style file viewer ("IDE") — tabbed, dark/light, source files
  reconstructed from ChromaDB chunks with a filesystem fallback.
  - A streaming README auto-generator (GET /repos/{id}/generate-readme) that
  feeds the diagram + code samples to an LLM and streams a full README.md.
  - QA telemetry — every chat answer writes a qa_queries row (chunks
  retrieved/kept, retrieval vs LLM latency, highlight hit, rewritten question)
  exposed via GET /chat/metrics/{session_id}.

  ---
  2. How AI-driven is it, exactly

  This is the heart of your question. The honest answer: the flagship 
  intelligence is LLM-produced and properly orchestrated; the deterministic 
  parts (AST, embeddings, retrieval, layout) are deliberately not LLM-reliant, 
  which is the right design.

  2.1 LangGraph — real and wired, not decorative

  Two compiled StateGraphs in backend/app/agents/graph.py:

  Analysis graph (graph.py:38-65):
  git_cloner → ast_parser → embedder → architect → critique
                                                └─[conditional]→ architect
  (retry) | END
  - The conditional edge should_continue_after_critique (graph.py:20-36): loops
  back to architect if critique failed AND retry_count < MAX_CRITIQUE_ATTEMPTS
  (3); otherwise END. This is a real reflection/retry loop, and
  architect.py:113-118 actually reads critique_feedback from state on retry and
  injects it via CRITIQUE_FEEDBACK_TEMPLATE — so regeneration addresses the
  reviewer's notes rather than blindly retrying.

  QA graph (graph.py:70-79): single node qa_agent, but that node internally runs
  the full multi-step RAG (see 2.3).

  State is typed (state.py): AnalysisState and a separate QAState (the spec's
  two-state intuition is honored). progress_log uses Annotated[..., 
  operator.add] for append-only merging across nodes — a real LangGraph idiom.

  ▎ Caveat: langgraph==0.0.31 is pinned in requirements.txt — a very early, 
  ▎ pre-1.0 release. It works, but it's ancient and you're missing years of API 
  ▎ improvements.

  2.2 The diagram is LLM-generated (this is the flagship, and it's real)

  architect.py builds a system prompt defining a strict AWS-style layered 
  vocabulary, sends repo_url + per-file summaries (first 2 AST chunks each,
  capped to 250 lines), and demands JSON-only output of {nodes[], edges[]} with
  typed layer / type / relation fields (architect.py:12-95). The LLM it calls is
  MODEL_DIAGRAM = openai/gpt-oss-120b:free via get_diagram_llm() (120B OSS
  reasoning model).

  critique.py then sends the actual file list + the generated {nodes, edges} to
  MODEL_CRITIQUE (same 120B) and asks for {critique_passed, critique_feedback},
  with explicit "be VERY lenient… nodes are architectural abstractions, not file
  names" guardrails (critique.py:21-51). On any technical error it fails open
  (accepts the diagram) so the pipeline never dead-locks (critique.py:120-136) —
  sensible for a free-tier-dependent system.

  So: the single most important visual artifact is produced by an LLM and
  quality-controlled by a second LLM in a loop. That's the core AI drive.

  2.3 Q&A is real RAG, engineered honestly

  qa_agent.py is the most sophisticated file in the repo. The streaming path
  astream_qa_answer (qa_agent.py:463-780) does, in order:

  1. Query rewriting (rewrite_query, with a hard 5s asyncio timeout, skipped
  when no history) using a separate cheap model (MODEL_REWRITE = 
  nemotron-3-nano-30b-a3b), so rewrites don't burn the main model's budget.
  2. Embed the rewritten query with the same local model used at indexing
  (embed_query_async) — query/index symmetry is guaranteed because both go
  through get_embeddings().
  3. Retrieve top-k=8 from the repo's ChromaDB collection; filter by
  cosine-distance relevance threshold 0.88; exclude chunks flagged embed_failed;
  adaptive fallback to the 2 closest chunks if the threshold drops everything.
  4. Ground the LLM with a system prompt containing explicit anti-hallucination
  "Honesty Rules" and the real list of diagram node IDs (_build_system_prompt,
  qa_agent.py:58-92). The model can only pick from valid node IDs.
  5. Stream tokens live (llm.astream); fall back to plain invoke_with_fallback
  if streaming errors.
  6. Validate the model's highlight_node_id server-side via strict exact-match
  against the valid set (_validate_node_id, qa_agent.py:201-212) — returns "" if
  the model hallucinated a node. This is the real mechanism behind the "chat
  highlights a diagram node" feature.
  7. Emit a metrics event (retrieval_ms, llm_ms, chunks kept/retrieved,
  rewritten question) persisted to the qa_queries table.

  Source files returned are the actual retrieved chunk paths, not LLM claims
  (qa_agent.py:359-363) — a deliberate anti-confabulation choice. This is
  textbook RAG done with care.

  2.4 LLM client engineering (why it survives the free tier)

  core/llm.py and core/config.py reveal a hardened setup:

  - Per-agent model routing via env (config.py:14-23): diagram + critique on the
  strong openai/gpt-oss-120b:free; chat, rewrite, and fallback on the fast
  nvidia/nemotron-3-nano-30b-a3b:free.
  - Retry with exponential backoff on transient errors — 429, rate, connection,
  timeouts, and 5xx (_is_retryable, llm.py:21-32), plus separate retry for
  JSON-parse failures.
  - Robust JSON extraction (_extract_json, llm.py:35-64): strips markdown
  fences, slices to outermost {...}, handles leading prose and empty/None
  content from "reasoning-only" models.
  - Multi-model fallback chain (invoke_with_fallback, llm.py:161-185):
  gpt-oss-120b → nemotron-3-nano → gemma-4-26b → llama-3.3-70b.
  - All calls go through OpenRouter free tier (single HTTP base, HTTP-Referer: 
  repohawk.app). The fact that the very agents I dispatched to map this codebase
  died on HTTP 429 is exactly the failure mode this retry/fallback layer exists
  to absorb at runtime.

  2.5 The README generator — a third LLM surface

  repos.py:608-760 /generate-readme is a separate streaming LLM task: it
  assembles the diagram's node list (labels, types, layers, tech, descriptions)
  + 10 deduplicated ChromaDB code samples, prompts the model as "expert
  technical writer / OSS maintainer," and streams the README markdown back over
  SSE. It even disconnects early if the client drops (await 
  request.is_disconnected()).

  2.6 Where AI is deliberately not used (good)

  Tree-sitter AST → chunking, embedding generation, vector retrieval, graph
  auto-layout (dagre), file/dependency parsing, and confidence scoring are all
  deterministic. The LLM only sees summaries, never the raw repo, and is only
  invoked for the genuinely generative tasks (diagram, critique, answers,
  README, title). That separation is exactly why this is cheap to run on
  free-tier models and why it's defensible.

  4. Architecture & stack (as it actually exists)

  Backend — FastAPI async, SQLAlchemy 2.0 async, Alembic. main.py wires repos,
  chat, auth routers. The analysis run is a BackgroundTasks job (repos.py:71)
  calling run_repo_analysis (services/analysis.py), which drives
  analysis_graph.astream() with a per-step 300s timeout (analysis.py:88-94) and
  publishes each node's progress_log to an in-process pub/sub (core/progress.py
  → progress_manager). The SSE endpoint (repos.py:111-168) subscribes a per-repo
  asyncio.Queue, replays persisted logs for already-complete repos, and emits
  pings on idle. On startup, recover_stale_analyses (analysis.py:20-48) flips
  any running/queued repos to failed so crashed runs don't spin forever.

  Data layer — 7 tables: users, password_reset_tokens, repos, diagrams,
  chat_sessions, chat_messages, qa_queries. All repo/diagram/chat/qa rows carry
  a user_id FK (auth added in d896bda); every endpoint filters by
  current_user.id. ChromaDB is embedded (core/vector_store.py — PersistentClient
  at backend/chroma_db/, one collection repo_{uuid_undercored} per repo) — no
  separate vector server, consistent with docker-compose.yml (only postgres runs
  as a service). Embeddings are local sentence-transformers
  (core/embeddings.py, LRU-cached, async variants) — zero embedding API cost and
  zero query latency after model warm-up.

  Frontend — Next.js 16 App Router, React 19, TanStack Query, Zustand, React
  Flow + dagre, framer-motion, shadcn-style UI, react-syntax-highlighter,
  html-to-image (PNG export). Highlights:
  - A BFF proxy layer under src/app/api/{repos,chat,auth}/* (Next route
  handlers) forwards to FastAPI with cookie/token forwarding (1455d41). The
  frontend talks only to these proxy routes.
  - useRepoAnalysis.ts consumes the analysis SSE via EventSource on
  /api/repos/{id}/stream, dedups logs, and wires stop/retry.
  - useDiagram.ts holds highlight state (the spec's useDiagram.js obligation,
  honored).
  - Diagram canvas: components/diagram/ (DiagramCanvas, LayeredArchitecture,
  ArchNode/AwsArchNode, AwsFlowEdge, MetadataPanel) — real React Flow layered
  rendering, not Mermaid.
  - Chat: components/dashboard/QAChatPanel, sessions sidebar (RepoSidebar),
  README modal, search modal.

  5. Honest assessment & notable issues

  Strengths
  - The agent/RAG design is real and non-trivial — two LangGraph graphs, a
  critique→regenerate reflection loop, grounded RAG with anti-hallucination +
  server-side highlight validation, three distinct LLM tasks, and a genuinely
  hardened free-tier LLM client.
  - Clean layering is largely respected: LLM calls live in agents/ +
  core/llm.py; DB writes go through routes/services; routers stay thin.
  - Operational maturity: per-step timeouts, stale-analysis recovery on restart,
  retry/cancel/stop/retry-with-cleanup, path-traversal guard on /file
  (repos.py:413-420, using commonpath not prefix-match), chat rate limiting, JWT
  secret enforced (refuses to start on "change-me"), CORS lockdown, shallow
  clones + 100KB file cap + MAX_CHUNKS=500 as DoS limits.

  Gaps / risks worth knowing
  1. Spec flagship features missing: staleness (F-04), share page (F-05), and
  the whole REPOHAWK.md export + CLI + VS Code extension (F-07) — the
  differentiator — are absent. If those matter for the product story, they're
  net-new work, not polish.
  2. file_node_index never built. The "sacred" table the spec said powers both
  highlight sync and staleness doesn't exist. Highlight sync works anyway
  (frontend-supplied valid_node_ids), but staleness has no backing structure now
  — it'd be greenfield from the schema columns up.
  3. Stale/confidence columns are dead weight (diagrams.stale*,
  confidence_file_count, contributing_files) — present, never written. Either
  wire them or drop them so the schema isn't misleading.
  4. Stale doc: embedder.py docstring claims it uses the OpenRouter embedding
  API; the code uses local sentence-transformers (config.py is correct). Anyone
  reading the node header will be misled.
  5. langgraph==0.0.31 is pinned at a pre-1.0 release — functional but old;
  upgrading is a real (if bounded) maintenance task.
  6. Leftover RSA private key on disk:
  frontend/src/secret_files/repohawk.2026-07-01.private-key.pem is a real
  -----BEGIN RSA PRIVATE KEY----- (I read only the header line). It is
  gitignored (frontend/.gitignore:25 *.pem) and not tracked by git (git ls-files
  returns nothing), so it was never committed — but the GitHub App integration
  it belonged to was removed in commit 7e2002f, so the file is now
  orphans-on-disk. Rotate/revoke that key in GitHub and delete the file; it
  shouldn't linger in the repo working tree.
  7. Single-token-budget dependency on free-tier OpenRouter. The whole product's
  quality ceiling is set by gpt-oss-120b:free and nemotron-3-nano:free. The
  retry/fallback machinery is excellent, but a future where those free models
  disappear or degrade would require re-pointing MODEL_* (which, to be fair, is
  one env change — the routing design pays off here).
  8. Memory drift: my own project memory (~85 days old) says "README is empty,
  just # RepoHawk" and "ChromaDB server in compose" — both now wrong. The README
  is a polished 8KB, and ChromaDB is embedded. (Flagging so you don't trust
  stale notes; I did not write any memory files this session per your no-edit
  instruction.)

  ---
  6. Bottom line

  RepoHawk is a real, working agentic codebase-intelligence product, not a demo.
  Its AI drive is concentrated where it should be — LLM-generated +
  LLM-critiqued architecture diagrams and grounded, streaming,
  anti-hallucination RAG chat — with the deterministic heavy lifting (AST,
  embeddings, retrieval, layout) kept off the LLM path. The LLM client is more
  robust than most production code I see (retry, JSON-recovery, model fallback,
  timeouts, stale-recovery).

  It is not the full REPOHAWK.md vision: the staleness detector, share page, and
  the REPOHAWK.md/CLI/VS-Code differentiator are unbuilt, the "sacred"
  file→node index was rearchitected away, and rendering switched from Mermaid to
  React Flow. If you're planning the next phase, those four gaps plus a
  langgraph upgrade, the empty confidence/stale columns, and the lingering
  private key are the highest-value items to address.
